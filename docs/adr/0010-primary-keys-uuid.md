# ADR 0010: Primary keys: UUIDs

**Status:** Accepted

## Context

Todos, tags, and users are addressed by ID in API URLs (e.g. `/todos/:id`). The API runs as multiple instances, and users must never reach other users' data.

## Problem it solves

Choosing an ID format that is hard to guess and can be generated by any instance.

## Decision

Use **UUIDs** (preferably time-ordered UUIDv7) as primary keys for all tables.

## Pros

- Not guessable, so enumeration (trying `/todos/41`, `/42`, `/43`) does not work.
- Does not reveal how many users or todos exist.
- Any API instance can generate IDs without coordinating with the database.

## Cons / tradeoffs

- Larger than integers (16 vs 4-8 bytes), so larger indexes.
- Fully random UUIDs (v4) fragment indexes; time-ordered v7 largely avoids this.
- Not human-readable, which makes debugging slightly harder.

## Alternatives considered

| Alternative             | Why rejected                                                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Auto-increment integers | Guessable and reveal volume; smaller and faster, but the security and multi-instance benefits of UUIDs outweigh this at our scale. |
| Random UUIDv4           | Works, but causes more index fragmentation than v7.                                                                                |

## Consequences

UUIDs are **defense in depth only**. The real protection is the ownership check on every query (`WHERE id = ? AND user_id = ?`), returning 404 for resources that are not the caller's.
